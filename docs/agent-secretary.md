# 에이전트 비서 Really

> **상태: 초안 (2026-10-15)** · 이름 **Really**(임시) · 에이전트 자리는 규칙 카드 생성(RAG)과 Really 두 곳이다([C-10](#6-제약사항)).
>
> **한 줄 요약:** 비서는 판정하지 않는다. 사용자가 **답하고, 이해하고, 세무대리인에게 넘기는** 일을 돕는다.
> 제안은 비서가, 확정은 사용자가, 판정은 룰엔진이 한다.

---

## 1. 개요

### 무엇을 만드나

화면 우측 하단의 버튼으로 여는 **대화형 비서**와, 서비스 곳곳에서 먼저 도움을 주는 **화면 속 도움**이다.
둘은 같은 비서이고 같은 도구를 쓴다.

| 한다 | 하지 않는다 |
|---|---|
| 되묻기 답을 돕는다 (지난번 답 불러오기, 말로 답하기) | 판정하거나 판정을 바꾼다 |
| 판정 이유와 근거 조문을 쉬운 말로 풀어 준다 | 세무 조언, 안분 비율 제안, 세액 제시 |
| 내 거래·합계를 찾아 준다 | 사용자 확인 없이 데이터를 바꾼다 |
| 사용법·용어·다음 할 일을 안내한다 | 법령을 검색해 새 근거를 만든다 |
| 세무대리인에게 물을 질문으로 정리해 준다 | 신고·제출·외부 발송 |
| | 답에 따라 판정·금액이 어떻게 바뀌는지 미리 알려 준다 |

### 사용자 니즈

대상은 1인 IT 사업자(강의 병행)다. 세무를 잘 모르고, 월 1회 업로드하고, 5월에 몰아서 정리한다.

| 니즈 | 지금 막히는 이유 | 비서가 하는 일 |
|---|---|---|
| "이거 또 물어봐?" | 되묻기 답(UserFact)이 업로드 단위라 업로드마다 같은 질문이 반복된다 | 지난번 답 불러오기 |
| "왜 이 판정이야?" | 판정 응답의 설명(`explanation`)에 채울 출처가 없다 | 판정 데이터와 조문으로 풀어 설명 |
| "이게 뭐였더라?" | PG 결제, 영문 가맹점, 몇 달 전 결제 | 같은 날 거래 같은 단서 제시 |
| "다음엔 뭘 해?" | 업로드 → 문진 → 판정 → 질문 → 요약 흐름에서 남은 일이 흩어져 있다 | 다음 할 일 안내 |
| "이거 경비 돼요? 몇 %로 해요?" | 서비스는 세무 조언을 하지 않는다 | 거절로 끝내지 않고 세무대리인 질문으로 바꿔 준다 |

마지막 줄이 이 서비스다운 비서의 핵심이다. 설계 원칙 "최악의 결과가 틀린 답이 아니라 질문 하나 더"를 대화에도 적용한다.

### 용어

| 용어 | 뜻 |
|---|---|
| 되묻기 (Question) | 룰엔진이 판정에 필요한 사실을 사용자에게 묻는 질문 |
| UserFact | 되묻기에 대한 답. 업로드(batch) 단위로 저장된다 |
| 소명 대기 | 불가로 추정했지만 사용자가 사정을 밝히면 풀리는 거래 (주말·공휴일 식대, 생활용품) |
| 사람 게이트 | 사람이 확인해야 다음으로 가는 지점. ① 판정 전 확인, ② 되묻기 |
| 제안 카드 | 비서가 만든 실행 대기 동작. 사용자가 [적용]을 눌러야 실행된다 |
| 핸드오프 | 세무대리인에게 넘길 질문과 자료 정리 |

## 2. 동작 방식

### 하나의 비서, 세 가지 모습

| 모습 | 언제 | LLM |
|---|---|---|
| **먼저 말 걸기** | 판정 완료, 업로드 차단처럼 코드가 아는 순간 | 쓰지 않는다 |
| **화면 속 도움** | 질문 카드의 지난번 답, "왜?" 버튼 | 대부분 쓰지 않는다 |
| **대화** | 사용자가 패널에서 묻는다 | 쓴다 (도구 호출 에이전트) |

코드가 이미 아는 순간에는 화면이 도구를 직접 부른다. LLM에게 "무슨 도구를 부를까"를 묻지 않는다.
그래야 빠르고, LLM이 죽어도 동작하고, 같은 상황에서 늘 같은 결과가 나온다.

### 구조

```
브라우저   비서 패널 · 화면 속 도움 · 제안 카드 ──[적용]──▶ 기존 API   ← 쓰기는 여기서만
   │ /api/v1
백엔드     인증 · 소유권 · 호출 한도 · AI 서버 중계 · 조회 API
   │ 내부망 (AI 서버는 외부에 노출하지 않는다)
AI 서버    에이전트 루프 ── 도구 (백엔드 조회 API를 사용자 권한으로 호출)
           검증기 (숫자 · 조문 · 근거 · 금칙어) · 도움말 문서 · Langfuse 추적
```

`judge()`는 이 그림 어디에도 없다. 제안이 [적용]되면 기존 API가 평소처럼 UserFact를 만들고 룰엔진이 다시 판정한다.

### 대화 한 턴

1. 시스템 프롬프트, 화면 맥락(지금 화면·업로드·보고 있는 대상), 최근 대화를 모델에 보낸다.
2. 모델이 도구를 부르면 실행하고 결과를 돌려준다. 병렬 호출을 허용하고, 한 턴에 최대 5회.
3. 최종 답을 검증한다. 실패하면 사유를 붙여 다시 시키고, 3회 실패하면 정해 둔 문구로 대신한다.
4. 답변과 제안 카드를 함께 돌려준다.

### 권한 원칙

| 구분 | 누가 실행하나 | 예 |
|---|---|---|
| 읽기 | 비서가 바로 실행. 권한은 사용자와 같다 | 진행 상황, 거래, 판정, 질문, 합계 |
| 쓰기 | 비서는 제안 카드만 만들고, 사용자가 [적용]을 눌러야 실행 | 질문 답, 분류, 화면 이동 |
| 금지 | 누구도 실행하지 않음 | 판정, 판정 실행, 비율·금액 권고, 외부 발송 |

### 3.1 지난번 답 불러오기

**왜 필요한가.** UserFact는 업로드 단위라 다른 업로드에 자동으로 적용되지 않는다(api.md 3.10). 그래서 매달
같은 통신비·구독 질문을 다시 묻는다. 이 결정은 그대로 두고, 다른 업로드의 답을 **읽어서 제안만** 한다.

**질문마다 등급이 다르다.** 건마다 사정이 다른 질문까지 과거 답으로 채우면 오탐이 난다.

| 등급 | 대상 | 처리 |
|---|---|---|
| A. 이어받기 | 가맹점 단위로 묻는 고정비 6종: 통신, 구독, 수도광열, 임차료, 보험, 금융 | 직전 답을 보여 주고, 여러 개면 확인 목록으로 한 번에 적용 |
| B. 이력만 | 같은 가게를 반복해서 가는 건별 용도 질문(카페, 음식점, 배달 등), 해외 SaaS 결제 기간 | "이 가맹점 지난 답: 업무미팅 6 · 개인 1"만 보여 준다. 미리 고르지 않는다 |
| C. 띄우지 않음 | 소명 대기, 자산·전자기기, PG미상·온라인쇼핑, 경조사, 손해배상, 적격증빙 | 건마다 따로 답해야 한다. 소명 대기를 일괄 응답에서 뺀 이유(#103)와 같다 |

**규칙**
- 같은 사용자의 다른 업로드에서, 같은 묶음 키와 같은 **질문 코드**로 답한 최신 값을 쓴다.
  답 종류(fact_type)가 아니라 질문 코드로 맞춘다. 구독과 통신은 같은 `전용여부`를 쓰지만 선택지가 다르다.
- 지금 질문의 선택지에 없는 값은 버린다.
- 최근 두 업로드의 답이 다르면 충돌로 보고 이력만 보여 준다.
- 일괄 응답으로 닫은 답은 출처를 표시해 약한 근거로 다룬다.
- 적용은 기존 질문 응답 API를 그대로 쓴다. 현재 업로드에 새 UserFact가 생기고 룰엔진이 다시 판정한다.
- 출처는 기록하되 다른 업로드의 행에 외래키로 잇지 않는다. 옛 업로드를 지울 수 없게 된다.

**문구는 사실 그대로 쓴다.** "AI 추천"이 아니라 「9월 업로드(국민)에서 '업무 전용'으로 답했습니다」.

## 4. 도구 목록

도구는 AI 서버에 있는 얇은 래퍼다. 백엔드 API를 사용자 권한으로 부르고, 도구 안에서는 LLM을 쓰지 않는다.

| 구분 | 도구 | 하는 일 | 단계 |
|---|---|---|---|
| 상황 | `get_status` | 업로드 목록, 문진 요약, 분류 대기, 판정 상태, 남은 질문, 다음 할 일 | 2 |
| 조회 | `list_questions` | 질문 그룹과 지난번 답 (A·B·C 등급) | 2 |
| | `find_transactions` | 조건 검색과 합계, 특정 거래의 앞뒤 거래 | 2 |
| | `get_judgment` | 판정 상세, 이 판정을 만든 답, 근거 조문 원문 | 2 |
| | `get_summary` | 판정별·계정별 합계, 미해소·미분류 | 2 |
| | `list_unclassified` | 분류 확인을 기다리는 가맹점과 후보 카테고리 | 2 |
| 도움말 | `get_help` | 사용법, 용어, 질문 뜻, 서비스가 하지 않는 일 | 2 |
| 제안 | `propose_answer` | 질문 답 | 2 |
| | `propose_classification` | 가맹점 분류 | 2 |
| | `propose_navigation` | 화면 이동 | 2 |
| | `propose_bulk_answer` | 남은 질문 일괄 답 | 2 |
| | `propose_override` | 판정 수정 | 2 |
| | `add_handoff_note` | 세무대리인 질문 추가 | 2 |

도구는 2단계부터 에이전트가 쓴다. 그중 지난번 답 조회, 진행 상황, 도움말은 1단계에서 화면이 먼저 직접 쓰는 백엔드 기능이고,
2단계에서 같은 기능을 도구로 감싼다. 화면과 에이전트가 같은 결과를 내도록 계산은 한 곳에만 둔다.

### 제안에는 근거가 있어야 한다

근거가 없으면 도구가 거절한다. 그래서 모델이 그럴듯하다는 이유만으로 답을 제안할 수 없다.

| 근거 | 허용 조건 |
|---|---|
| 사용자 발화 | 인용한 문장이 이 대화의 사용자 메시지에 실제로 있고, 그 대상(가맹점 이름이나 날짜·금액)을 가리킨다 |
| 지난번 답 | 이 대화에서 `list_questions`가 그 질문에 A등급(충돌 없음)을 돌려줬다 |
| 후보 카테고리 | 서버가 준 그 가맹점의 후보 안에 있다 |

소명 대기 질문은 사용자 발화가 근거일 때만 제안할 수 있다. 이때 인용 문장에 그 건을 특정하는 날짜나 금액이 있어야 한다.
없으면 도구가 `AMBIGUOUS_TARGET`으로 거절하고, 모델은 어느 건인지 사용자에게 묻는다.
모델의 판단에 맡기지 않고 코드로 지키는 규칙이라 모델을 바꿔도 유지된다. 비교에서 Luna는 이 검사 없이 해당 유형을 3/3 틀렸고, 검사를 넣자 9/9 통과했다(8장).

소명 대기가 아닌 질문, 분류, 판정 수정도 인용 문장에 그 가맹점 이름이나 날짜·금액이 있어야 한다.
"남은 질문 전부 개인" 같은 말을 건마다 붙이면 일괄 답 규칙(남은 그룹 5개 이하)을 우회한다. 평가에서 Luna가 실제로 그렇게 했다.
한꺼번에 하는 말은 `propose_bulk_answer`로만 처리한다.

### 도구 공통 규칙

- UUID는 턴 단위의 짧은 별칭(`t3` 거래, `g2` 질문 그룹, `c1` 분류 그룹)으로 바꿔 모델에 준다. 모델은 긴 ID를 옮겨 적다 자주 틀린다.
  대화 기록을 서버에 두지 않으므로(C-12) 다음 턴에는 도구로 다시 찾는다.
- 목록은 15~20개까지만 주고 전체 건수를 함께 준다. 합계는 잘린 목록이 아니라 전체 기준이다.
- 숫자·합계는 도구가 계산한다. 모델이 더하지 않는다.
- 오류는 예외가 아니라 결과로 돌려준다. 모델이 사유를 보고 고쳐서 다시 부른다.
- 도구 스키마는 strict 모드로 정의한다. strict를 받지 않는 모델(게이트웨이의 Haiku 5.5)에는 끄고 보낸다. 인자 검사는 어느 모델이든 도구 안에서 똑같이 한다.
- 화면별로 도구를 골라 보여 준다. 한 화면에 9개 이하로 둔다.

### 일부러 만들지 않는 도구

| 없는 도구 | 이유 |
|---|---|
| 판정·재판정 | 판정은 룰엔진만 한다 |
| 판정 실행 시작 | 사람 게이트 ①을 건너뛴다. 확인 화면으로 안내만 한다 |
| 문진·업로드 변경, 업로드 삭제 | 판정의 전제를 바꾸거나 되돌릴 수 없다 |
| 비율·금액 권고 | 세무 조언이다 |
| 법령 검색 | RAG 범위 밖이고 근거 오적용 위험이 있다 |
| 바로 실행되는 쓰기, 외부 발송 | 쓰기는 사용자 클릭으로만 한다 |

## 7. LangChain을 쓰지 않는 이유

**결론:** LangChain을 써도 실행 속도는 거의 같다. 문제는 LangChain이 대신 짜 주는 부분이 작다는 것이다.
우리가 실제로 짤 코드는 그대로 남고, 프레임워크의 확장 지점에 맞춰 써야 한다. 여기에 고정 비용과 추적 충돌이 붙는다.

### 측정 (2026-10-15, LangChain 1.4.6 · langchain-openai 1.7.2 · LangGraph 1.2.15)

| 항목 | openai SDK 직접 | LangChain | 차이 |
|---|---|---|---|
| 설치 패키지 | 14개 | 44개 | +30개 |
| 디스크 | 53 MB | 92 MB | +39 MB |
| import 시간 | 약 0.66초 | 약 1.61초 | +약 0.95초 |
| import 직후 메모리 | 51 MB | 90 MB | +약 40 MB |
| 한 턴 (도구 1회 + 답, 로컬 가짜 서버) | 5.4ms | 8.3ms | +약 3ms |
| 요청 본문 | – | `stream: false`만 추가 | 사실상 같음 |

한 턴에 더 드는 3ms는 LLM 왕복(1~2초)에 비하면 무시할 만하다. 실행 속도는 반대 이유가 아니다.

### 이유

1. **대신해 주는 것이 작다.** LangChain의 에이전트 함수(`create_agent`)가 해 주는 일은 모델 호출, 도구 실행, 결과 전달의 반복이고, 직접 짜도 15줄 정도다.
   우리 코드의 대부분은 근거 검사, 별칭 변환, 화면별 도구 묶음, 제안 카드 수집, 최종 답 검증과 재시도다.
   LangChain을 써도 이 코드는 직접 짜야 하고, 미들웨어와 상태 주입 같은 확장 지점으로 옮겨질 뿐이다.
   그 결과 도구 함수가 프레임워크 타입에 묶인다.
2. **테스트와 디버깅이 어려워진다.** 규칙이 순수 함수와 작은 루프면 LLM 클라이언트만 가짜로 바꿔서 테스트할 수 있다.
   프레임워크 안에 넣으면 테스트에 그래프 실행기가 필요하고, 오류를 따라가는 경로가 길어진다.
3. **Langfuse 추적과 충돌한다 (확인함).** `ai/pipeline/llm.py`의 `import langfuse.openai`가 openai의 호출 메서드를 전역으로 감싼다.
   LangChain도 바로 그 메서드로 호출한다. 그래서 LangChain용 Langfuse 콜백을 붙이면 같은 호출이 두 번 기록된다.
   콜백을 안 붙이면 에이전트와 도구 구조가 사라지고 LLM 호출만 평평하게 남는다.
   지금 방식으로는 원하는 트리가 이미 나온다.
4. **고정 비용과 버전 결합이 크다.**
   - 의존성이 30개 늘어난다. LangGraph 5종, 쓰지 않는 추적 SDK인 langsmith, 두 번째 HTTP 클라이언트(`httpx`, `requests`)가 들어온다.
   - 프로세스마다 메모리가 약 40 MB 늘어난다. AI 컨테이너의 메모리 상한은 512 MB다.
   - `langgraph`가 마이너 버전 단위(`<1.3`)로 고정되고, `openai`에 `<4` 상한이 걸린다.
5. **쓰지 않는 기능이 부담이 된다.**
   - 체크포인터(대화 상태 저장)는 자체 테이블에 저장한다. 탈퇴나 업로드 삭제 때 CASCADE로 지우는 팀 삭제 정책 밖에 사용자 데이터가 생긴다.
   - interrupt(사람 승인 대기)를 쓰면 상태 없는 서버에 상태가 생긴다. 우리는 이미 제안 카드와 사용자 클릭으로 같은 일을 한다.
   - 여러 모델 공급자 지원과 검색 통합은 필요 없다.
6. **도구 스키마를 통제하기 어렵다.** 자동 생성 스키마에는 `strict`와 `additionalProperties: false`가 빠진다.
   정확한 스키마를 보내려면 결국 JSON 스키마를 직접 넘겨야 한다.

**다시 검토할 때:** 여러 모델 공급자를 오가야 할 때, 긴 작업을 멈췄다 이어가며 서버가 상태를 들고 있어야 할 때, 기성 통합을 그대로 쓸 때.

| 비서 모델 비교 | 가짜 도구 7개, 한 턴 시나리오 18개를 3회씩 돌렸다. Luna 51/54, Haiku 5.5 54/54. Luna가 틀린 것은 소명 대기 건이 여러 개일 때 묻지 않고 제안한 유형뿐이고, 4장의 날짜·금액 검사를 넣은 뒤 이 유형은 두 모델 모두 15/15 통과했다. 한 턴 중앙값 Luna 4.1초, Haiku 5.1초. 한 턴 비용 Luna 0.5원, Haiku 1.5원. Haiku는 같은 대화도 입력 토큰이 약 2배, 출력이 약 6배다 |

## 9. AI 서버 API (내부)

`POST /assistant/chat` — AI 서버(`ai:8000`) 내부 전용이다. 백엔드가 사용자 요청을 그대로 중계하고,
사용자의 `Authorization` 헤더를 함께 넘긴다. 비서의 조회 도구는 이 헤더로 백엔드 공개 API를 부른다.

**요청**

```json
{
  "message": "토요일 스타벅스는 클라이언트 미팅이었어",
  "history": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}],
  "context": {"screen": "/questions", "batchId": "0199aa11-...", "transactionId": null, "year": 2026},
  "sessionId": "browser-conv-1"
}
```

| 필드 | 규칙 |
|---|---|
| `message` | 1~1,000자 |
| `history` | 최근 메시지 20개 이하. 각 `user` 또는 `assistant`, 2,000자 이하. 서버는 저장하지 않는다(C-12) |
| `context.screen` | 지금 화면 경로. 화면별 도구 묶음을 고르는 데 쓴다 |
| `context.batchId` · `transactionId` · `year` | 지금 보고 있는 업로드·거래와 귀속연도. 없으면 null |
| `sessionId` | Langfuse 세션 묶음용. 영문·숫자·`-`·`_`, 64자 이하 |

**응답 200**

```json
{
  "answer": "토요일 스타벅스 결제가 두 건 있습니다. ...",
  "proposals": [{"kind": "answer", "questionIds": ["..."], "value": "업무미팅", "source": "ASSISTANT", "card": "스타벅스 서면점 9/12 12,800원 → '업무미팅'"}],
  "traceId": "0ba0fb7f..."
}
```

`proposals`는 사용자가 [적용]을 눌렀을 때 프론트가 부를 API의 요청 본문이다. 프론트는 AI가 만든 경로를 그대로 호출하지 않고 `kind`로 API를 고른다.

| kind | 필드 | [적용] 시 호출 |
|---|---|---|
| `answer` | `questionIds`, `value`, `source`(`ASSISTANT`·`PREVIOUS_ANSWER`) | `POST /question-responses` |
| `bulk_answer` | `batchId`, `factType`, `value` | `POST /questions/bulk-answer` |
| `classification` | `reviewIds`, `merchantCategory` | `POST /classification-responses` |
| `override` | `judgmentId`, `toVerdict`, `reason` | `POST /judgments/{id}/override` |
| `handoff_note` | `text`, `transactionIds` | 신규 세무대리인 질문 저장 API |
| `navigation` | `route` | 화면 이동 |

모든 카드에는 사용자에게 보여 줄 한 줄 요약 `card`가 있다.

**오류:** 422 요청 검증 실패, 429 동시 실행 한도 초과(`Retry-After`). LLM이 실패해도 5xx를 내지 않고 폴백 답을 준다.

## 10. 다른 파트에 필요한 것

형태는 각 담당이 정한다. 여기서는 무엇이 필요한지만 적는다.

**백엔드**
- **비서 중계 `POST /api/v1/assistant/chat`:** 인증, `batchId` 소유권 확인, 사용자별 한도(동시 1, 분당 10, 하루 100),
  AI 서버로 헤더·본문 전달(타임아웃 35초 이상), 오류를 api.md 1.3 형식으로 변환
- **진행 상황 `GET /progress?batchId`:** 업로드 요약, 문진(버전·기장의무·직원 유무만. 수입·이름·이메일 제외), 분류 대기 수·금액,
  최근 판정 실행 상태, 미답변 질문 수·금액과 지난번 답으로 채울 수 있는 수, 다음 할 일(`step`, `route`)
- **지난번 답 `GET /questions/suggestions?batchId`:** 미답변 질문 그룹마다 `groupKey`, `factType`, `code`, 등급(`A`·`B`·`C`),
  A면 `value`·`sourceLabel`(예: "9월 업로드(국민)")·`conflict`·`history`, B면 `historyCounts`, C면 `reason` (등급 규칙은 3.1)
- **필드 추가:** 질문 응답에 `code`, `POST /question-responses` 요청에 `source`
- **세무대리인 질문 저장 API:** 사용자 소유, 탈퇴 시 삭제. 요약의 "세무대리인에게 넘길 문장"에 포함한다
- **이미 계획된 API에 의존:** 판정 수정(A5), 일괄 응답(A7)

**프론트**
- 비서 버튼과 패널, 위 요청 모양으로 화면 맥락 전달, 제안 카드 표시와 `kind`별 [적용] 호출, 먼저 말 걸기
- 업로드 화면 "데이터 경계" 안내에 Really 항목 추가. 외부 모델로 보내는 데이터 목록은 AI 쪽이 정해서 넘긴다(QR-7)
