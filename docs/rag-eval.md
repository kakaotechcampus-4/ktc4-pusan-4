다른 세션이 이어받을 때 읽는 문서다. 이미 재본 것을 다시 재지 않고, 이미 실패한 것을
다시 시도하지 않게 하는 게 목적이다. 모든 수치는 실측이고 추정은 그렇다고 표시했다.

머지 시점 기준이다. 머지 후 트리에서 pytest 88건과 ruff 통과를 확인했다.

갱신 2026-09-23 저녁. §9 의 0~3단계 개선을 반영했다(feature/rag-architecture 작업트리,
미커밋). pytest 91건과 ruff 통과. §2·§3·§7 은 이 시점 기준으로 고쳤고, §6 에는 행을 더했다.

## 1. 먼저 읽을 것 — 하네스를 n=1 로 믿지 마라

같은 코드, 같은 설정으로 초안 하네스를 두 번 돌린 결과다.

| 지표 | 1회차 | 2회차 |
|---|---|---|
| 게이트 | 3/8 | 5/8 |
| 근거 적중 | 1/14 | 2/14 |
| 검색누락 | 12 | 10 |
| 오적용 | 9 | 10 |

검색 자체는 순수 SQL 이라 결정적인데 검색누락까지 흔들린다. 질의를 rewrite() 가
매번 새로 만들기 때문이다. LLM 비결정성이 질의 작성 · 근거 선택 · 초안 생성
세 군데에서 들어와 곱해진다. temperature=0 은 걸려 있지만 게이트웨이가 비트 단위로
결정적이지는 않다.

실행 6회를 모아 본 노이즈 대역이다.

| 지표 | 관측 범위 | 판별력 |
|---|---|---|
| 게이트 | 3 ~ 6 / 8 | 없음 |
| 근거 적중 | 1 ~ 2 / 14 | 없음 |
| 오적용 | 9 ~ 13 | 큰 효과만 |

**따라서 오적용 24 -> 11 정도(50% 이상)의 변화만 신호로 취급했다.** 게이트나 근거
적중이 1~2 움직인 것으로 판단한 결정은 근거가 약하다. 아래 "폐기" 항목 중 일부가
여기에 해당하며 그렇다고 표시해 뒀다.

**다음 세션이 제일 먼저 할 일은 이 재현성을 잡는 것이다.** 안 그러면 이후 모든
튜닝 판단이 같은 불확실성을 물려받는다.

**→ 해결했다(§9 0단계).** run_draft 도 질의 계획을 `eval/.plans.json` 에 고정한다. 그 뒤
같은 8키 3회의 흔들림은 게이트 0~2, 근거 적중 0~1 로 줄었다. 오적용은 대개 1~4 차이지만
한 키가 기본 조문을 통째로 인용한 회차에서 한 번에 13 이 튄 적이 있다(§9). 위 노이즈 대역은
대부분 rewrite() 에서 왔다. `--search-only` 로 재는 후보 재현율은 두 번 돌려 출력이 같다.
다만 선택·초안 단계는 여전히 조금 흔들리므로 3회 범위로 본다.

## 2. 현재 성적

| 하네스 | 무엇을 재나 | 결과 |
|---|---|---|
| eval.run_search | 검색이 정답 조문을 top-8 에 올리나 | 재현율 7/10, must_not 위반 2건(RC-009 법인세법 고시) |
| eval.run_draft --search-only | 카드 인용이 후보에 들어오나 (32키, 결정적) | 47/51 — 27·33조 44/44 · 그 외 3/7 |
| eval.run_draft | 후보 중 옳은 걸 골라 카드 초안을 쓰나 | 8키 3회: 게이트 6~8/8, 근거 적중 6~7/14, 오적용 9~11, 반대 1 |
| | | 32키 1회: 게이트 22/32, 근거 적중 21/51, 오적용 67, 반대 1 |

둘 다 손으로 돌린다. CI 에 없다. 재현율이 낮아(합의 당시 4/10) 게이트로 쓸 수 없다는 데
리뷰어와 합의했다.

```bash
cd ai
uv run python -m eval.run_search                   # 고정 질의. 모델 호출 0회
uv run python -m eval.run_search --rewrite         # SearchPlan 경로
uv run python -m eval.run_draft --search-only      # 후보 재현율. 계획 고정이라 결정적
uv run python -m eval.run_draft --limit 8 --fresh --show   # 선택·초안. 3회 돌려 범위로 본다
```

run_draft 의 질의 계획은 `eval/.plans.json` 에 고정돼 있다. 질의 프롬프트나 `context()` 를
바꿨으면 그 파일을 지우고 다시 재야 한다 — 지금 계획은 §9 0단계 시점의 context 로 만든 것이다.

잣대는 다르다. run_search 는 eval/golden.yaml(10건, 손으로 만든 기대 조문),
run_draft 는 rules/cards/*.yaml(47장, 사람이 검수한 실제 카드)을 (카테고리, 업종)
으로 묶어 쓴다.

  AGENT_*/EMBEDDING_* 를 ai 서비스에 넘기고 있어 배포 시 어긋난다.

  `chunk.clean()` 을 빼고 `reindex --full --doc-type=법령`, `--doc-type=행정규칙` 을 다시 돌린다.
- 심판례 청크는 본문 정리(개정 표기·한자 병기) 대상이 아니다. `<tbody>`·`<a>` 잔여 태그도 남아 있다.

## 9. 2026-09-23 저녁 — 0~3단계 개선

계획은 "측정을 결정적으로 → 27·33조를 전제로 → 청크 본문 정리 → 법령 조 단위 선택" 순서였다.
전부 feature/rag-architecture 작업트리에 있고 커밋하지 않았다.

### 진단 (읽기 전용, 모델 호출 0회)

- **정답이 두 조에 몰려 있다.** 카드 키별 인용 51건 중 44건이 27-1·33-1-*. 주제 질의로는
  27-1 이 32~233위, 33-1-5 가 81~913위다. 검색으로 찾을 대상이 아니라 게이트의 전제다.
- **RRF 가 융합을 안 하고 있었다.** 고정 질의 8건 중 6건에서 벡터·키워드 상위 30이 0~1건만
  겹쳤다. 점수가 1/61, 1/61, 1/62 … 로 번갈아 나와 top-8 이 사실상 각자 top-4 다.
- **k 를 올려도 소용없다.** k=8/16/32 모두 4/10 (시뮬레이션). 놓친 정답이 벡터 20~2,274위다.
- **한 조가 칸을 다 먹는다.** 형제 호가 같은 머리말(조 제목 + 항 도입문 + 개정일 목록)을 달아
  원칙 질의조차 한 조의 형제 호가 1~16위를 채웠다(§4).
- **조 단위로 뽑고 형제 잎을 같이 보여주면 7/10** (시뮬레이션). 조당 1청크만 남기면 2/10 으로
  오히려 나빠졌다 — 조를 맞혀도 정답 호가 최고점 잎이 아니다. 실측(3b)도 7/10 이었다.
