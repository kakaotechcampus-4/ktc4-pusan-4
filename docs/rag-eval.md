## 1. 먼저 읽을 것 — 하네스를 n=1 로 믿지 마라

같은 코드, 같은 설정으로 초안 하네스를 두 번 돌린 결과다.

| 지표 | 1회차 | 2회차 |
|---|---|---|
| 게이트 | 3/8 | 5/8 |
| 근거 적중 | 1/14 | 2/14 |
| 검색누락 | 12 | 10 |
| 오적용 | 9 | 10 |

검색 자체는 순수 SQL 이라 결정적인데 검색누락까지 흔들린다. 질의를 rewrite() 가
매번 새로 만들기 때문이다. LLM 비결정성이 질의 작성 · 근거 선택 · 초안 생성
세 군데에서 들어와 곱해진다. temperature=0 은 걸려 있지만 게이트웨이가 비트 단위로
결정적이지는 않다.

실행 6회를 모아 본 노이즈 대역이다.

| 지표 | 관측 범위 | 판별력 |
|---|---|---|
| 게이트 | 3 ~ 6 / 8 | 없음 |
| 근거 적중 | 1 ~ 2 / 14 | 없음 |
| 오적용 | 9 ~ 13 | 큰 효과만 |

**따라서 오적용 24 -> 11 정도(50% 이상)의 변화만 신호로 취급했다.** 게이트나 근거
적중이 1~2 움직인 것으로 판단한 결정은 근거가 약하다. 아래 "폐기" 항목 중 일부가
여기에 해당하며 그렇다고 표시해 뒀다.

**다음 세션이 제일 먼저 할 일은 이 재현성을 잡는 것이다.** 안 그러면 이후 모든
튜닝 판단이 같은 불확실성을 물려받는다.

**→ 해결했다(§9 0단계).** run_draft 도 질의 계획을 `eval/.plans.json` 에 고정한다. 그 뒤
같은 8키 3회의 흔들림은 게이트 0~2, 근거 적중 0~1 로 줄었다. 오적용은 대개 1~4 차이지만
한 키가 기본 조문을 통째로 인용한 회차에서 한 번에 13 이 튄 적이 있다(§9). 위 노이즈 대역은
대부분 rewrite() 에서 왔다. `--search-only` 로 재는 후보 재현율은 두 번 돌려 출력이 같다.
다만 선택·초안 단계는 여전히 조금 흔들리므로 3회 범위로 본다.

## 2. 현재 성적

| 하네스 | 무엇을 재나 | 결과 |
|---|---|---|
| eval.run_search | 검색이 정답 조문을 top-8 에 올리나 | 재현율 8/10, must_not 위반 2건(RC-009 법인세법 고시). 9/8 코퍼스에서는 7/10 |
| eval.run_draft --search-only | 카드 인용이 후보에 들어오나 (32키, 결정적) | 그 외 조문 5/8 (기본 조문 64/64). 후보 평균 24.8k자 |
| eval.run_draft | 후보 중 옳은 걸 골라 카드 초안을 쓰나 | 32키 3회. 아래 판정 기준표 (§12 · §15) |

둘 다 손으로 돌린다. CI 에 없다. 재현율이 낮아(합의 당시 4/10) 게이트로 쓸 수 없다는 데
리뷰어와 합의했다.

```bash
cd ai
uv run python -m eval.run_search                   # 고정 질의. 모델 호출 0회
uv run python -m eval.run_search --rewrite         # SearchPlan 경로
uv run python -m eval.run_draft --search-only      # 후보 재현율. 계획 고정이라 결정적
uv run python -m eval.run_draft --limit 8 --fresh --show   # 선택·초안. 3회 돌려 범위로 본다
```

run_draft 의 질의 계획은 `eval/.plans.json` 에 고정돼 있다. 질의 프롬프트나 `context()` 를
바꿨으면 그 파일을 지우고 다시 재야 한다 — 지금 계획은 §9 0단계 시점의 context 로 만든 것이다.
§13 의 업종 프로파일은 질의 작성에 넣지 않으므로(`context(..., profile=False)`) 계획은 그대로 유효하다.

10/9 저녁부터 수치는 gpt-6-luna(추론 none)로 잰 것이다(§15). `.env` 에 `AGENT_MODEL=openai/gpt-6-luna` ·
`AGENT_REASONING_EFFORT=none` 과 그 모델의 `AGENT_BASE_URL`(게이트웨이는 모델마다 다르다)을 둔다. 비우면
gpt-4o-mini 로 돈다.

잣대는 다르다. run_search 는 eval/golden.yaml(10건, 손으로 만든 기대 조문),
run_draft 는 rules/cards/*.yaml(51장)을 (카테고리, 업종)으로 묶은 32키를 쓴다. 휴일 카드와
카테고리 없이 키워드 · 금액으로만 걸리는 카드는 입력으로 재현할 수 없어 뺀다.

### run_draft 판정 기준

2026-10-07 에 바꿨다. 옛 지표를 왜 내렸는지는 §12 에 있다.

- 정답지는 카드 인용과 선택지 인용(`question.options[].citations`) 중 verified 인 것이다. 72건이다. 10/10 에
  5호 카드에 시행령 61-1-1 을 더하기 전에는 54건이었다(§16).
- 결론 지표는 정답 결론으로 키를 셋으로 나눠 센다. A 확인필요뿐 15키, B 가능 또는 불가 하나 15키,
  C 카드가 여럿이라 정답이 갈림 2키(해외SaaS · 기타). 10/9 저녁 게임 · 여가 카드가 불가로 바뀌기 전에는
  A 17 · B 13 이었다(§15).
- 오류 키(재시도 소진)는 결론 · G1 · 근거의 분모에서 빼고 오류 줄에서 따로 센다. 넣으면 오류가 늘 때
  ↓ 지표는 좋아 보이고 ↑ 지표는 나빠 보인다. 보류와 검색에는 넣는다 — 운영에서도 오류는 초안 없는
  보류 행이 되고, 검색은 오류 전에 끝난다.
- 기본 조문은 검색 없이 늘 후보에 붙는 소득세법 27·33조와 시행령 61·78조(`search.FRAME`)다. 시행령은
  10/9 에 넣었다(§14). 그 전 절의 근거 · 검색 수치는 27·33조 기준이다.
- ↓ 지표는 아무것도 안 하면 0 이 된다. 짝인 ↑ 지표와 같이 읽는다 — 과잉확정 · 반대와 확정 적중,
  전체 보류와 위험 결론 중 보류, G1 오판과 G1 적중, 카드 밖 인용과 적중.

| 줄 | 지표 | 정의 | 10/9 Luna 3회 |
|---|---|---|---|
| 결론 | 과잉확정 ↓ | A 중 가능 · 불가로 단정한 키 | 2/15 · 1/15 · 2/15 |
| | 반대 ↓ | B · C 중 정답의 확정값과 반대로 낸 키 | 0/17 · 0/17 · 0/17 |
| | 확정 적중 ↑ | B 중 정답과 같은 값을 낸 키 | 13/15 · 13/15 · 12/15 |
| 보류 | 위험 결론 중 ↑ | 과잉확정 · 반대 키 중 보류가 붙은 키 | 0/2 · 0/1 · 1/2 |
| | 전체 ↓ | 32키 중 보류. 검수 부담이다 | 0 · 0 · 1 |
| G1 | 오판 ↓ | 정답에 G1 이 없는 키 중 G1 을 낸 키 | 0/29 · 0/29 · 0/29 |
| | 적중 ↑ | 정답이 G1 인 키 중 G1 을 낸 키 | 3/3 · 3/3 · 2/3 |
| 근거 | 기본 조문 적중 ↑ | 정답 인용 중 기본 조문을 인용한 비율 | 57/64 · 59/64 · 56/64 |
| | 그 외 조문 적중 ↑ | 나머지 정답 인용을 인용한 비율. 놓친 것은 검색누락 · 선택누락으로 가른다 | 2/8 · 3/8 · 3/8 |
| | 키당 카드 밖 인용 ↓ | 정답에 없는 인용의 키당 평균 | 1.06 · 0.97 · 1.09 |
| 검색 | 그 외 조문 후보 재현율 ↑ | 그 외 정답 인용이 후보에 들어왔나. 결정적 | 5/8 |
| 오류 | 오류 ↓ | 재시도를 다 써서 초안이 안 나온 키 | 0 · 0 · 0 |

10/7 수치는 §12, 10/8 은 §13, 10/9 낮(gpt-4o-mini)은 §14 재기준에 있다. 4o-mini 를 다시 채점한 값은
§15 에 있다. 근거 줄은 10/10 정답지(§16)로 다시 채점한 값이다. 54건 정답지로는 기본 조문 42 · 43 · 41/46,
카드 밖 인용 1.53 · 1.47 · 1.56 이었다. §15 까지의 근거 수치는 54건 기준이다.

출력에는 이 줄들과 함께 정답 조문별 적중, 카드 밖 인용 조문별 건수(각 상위 5)가 찍힌다. 반대가
있으면 종료 코드가 1 이다.

## 7. 다음에 할 일 (우선순위)

§10 시점 목록의 1번(G1 오판)은 §11 에서 머리말이 원인인 것을 잡았다. 지금 순서다. 수치는 10/9 Luna
재기준(§2 기준표)이고, 5회 범위는 보정 실험 2회를 합친 것이다(§15). 4o-mini 때 남았던 재시도 소진 오류(보험

1. **운영 반영.** 운영 서버의 키 · 엔드포인트는 10/9 에 Luna 로 바꿨다. 배포된 코드는 모델 이름을

   compose 전달)가 배포되고 서버 env 에 `AGENT_MODEL=openai/gpt-6-luna` · `AGENT_REASONING_EFFORT=none` 이

   부르는 건 규칙 후보 배치뿐이고 트리거가 아직 없어(§8) 그 사이 깨지는 경로는 없다.
2. **과잉확정 1~2.** 여비교통(가능)이 5회 모두다. 보정 문구 "개인적으로 쓴 결제가 섞일 수 있다는 것만으로

   부족 보류로 잡혔다.

   가능 결론의 근거는 아니다.
5. **보류가 위험 결론을 거의 못 잡는다.** 과잉확정 · 반대 1~2키 중 보류는 5회 중 1번(보험)이다. 보류

## 9. 2026-09-23 저녁 — 0~3단계 개선

### 진단 (읽기 전용, 모델 호출 0회)
