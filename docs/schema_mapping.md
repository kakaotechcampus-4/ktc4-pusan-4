# 파서 출력 ↔ 노션 transaction 스키마 대조표

백엔드 협의용 문서다. 파서(`tools/parse_card_xls.py`)가 만드는 CSV 컬럼과
노션 `transaction` 필드를 맞춰본 것이다.

- 파서 출력: 15컬럼 (`tools/parsers/__init__.py` 의 `OUT_FIELDS`)
- 노션 transaction: 10필드
- 상호명은 익명화 규칙을 따른다 — 지점명·사업자번호는 이 문서에 쓰지 않는다

## 1. 대응 있음 (6)

| 파서 출력 | 노션 필드 | 비고 |
|---|---|---|
| `approved_at` | `approved_at` | 승인일. 청구일 아님. IBK 승인일시에서 날짜만, KB 이용일 |
| `raw_merchant` | `merchant_raw` | **이름만 다름.** 파일 원문 그대로. 20바이트 절단된 상태도 그대로 |
| `amount` | `amount` | 원화 승인금액(부가세 포함). 외화 전용 행은 현재 제외 |
| `installment_months` | `installment_months` | 일시불이면 0. **실데이터 미검증** — 표본이 전부 일시불이다 |
| `natural_key` | `natural_key` | **재료가 다르다.** 4장 참조 |
| `status` | `status` | `판정대상` / `취소상계` / `대상제외`. 파서가 붙인다 |

## 2. 스키마에만 있음 — 파서가 만들지 않는 것 (4)

| 노션 필드 | 누가 채우는가 | 비고 |
|---|---|---|
| `id` | DB | uuid PK |
| `batch_id` | DB | uuid FK. 업로드 단위 |
| `merchant_norm` | 백엔드 | `merchant_dict` 조회로 채운다. 파서가 키를 계산해 박으면 Python/Java 엔진이 갈라져 히트율이 조용히 0%가 된다 |
| `merchant_category` | 분류 엔진 | PG 블록 → 시드 사전 → 키워드룰 결과. 파서 단계가 아니다 |

### `status` 매핑 — 파서가 출력하도록 반영함

파서의 취소 페어링 결과를 `status` 로 직접 내보낸다.

| 파서 처리 | 제안 status | 근거 |
|---|---|---|
| 정상 기록 (`needs_review` 없음) | `판정대상` | 기본값 |
| 취소와 짝지어 제외한 원 결제 | `취소상계` | 승인번호 또는 상호+금액+날짜로 짝이 1건 확정된 경우 |
| 취소 행 자체 | `취소상계` | 지출이 아니다 |
| 비거래 항목 (정상할인·포인트사용) | `대상제외` | 카드사가 만든 정산 행 |
| 합산 행 (`is_aggregated`) | `판정대상` | 제외하지 않는다. 여비교통 후보 |
| 취소 대상 불확정 (`needs_review`) | **`판정대상` + needs_review** | 아무것도 상계하지 않았다. 사용자가 답해야 확정된다 |
| 금액 파싱 불가 | `대상제외` | `review_reason` 에 사유를 남긴다 |

`review_reason` 에 제외·상계 사유가 들어간다.

```
취소 상계 (승인번호 매칭)
취소 상계 (폴백 매칭)
취소 행 (승인번호 매칭으로 상계됨)
취소 행 (짝 후보 없음 — 원 결제가 조회 기간 밖일 수 있다)
취소 행 (합산 행 — 개별 취소 대상이 없다)
비거래 항목 (카드사 정산 행)
취소 대상 불확정 — 같은 상호·금액 결제가 N건이라 어느 건이 취소됐는지 자동 판정 불가
```

**파서는 모든 행을 내보낸다.** 상계·제외된 행을 CSV 에서 빼면
"카드 명세서는 300만원인데 앱은 280만원" 을 설명할 근거가 사라진다.
`raw_merchant` 원문을 덮어쓰지 않는 것과 같은 이유다. 필터링은 백엔드가 한다.

측정값(입력 356행):

```
전체 출력  356건
  판정대상  326건
  취소상계    2건
  대상제외   28건   (정상할인 8 / 편의점할인 16 / 대중교통할인 1 등)
```

커버리지·분류 통계는 `status=판정대상` 기준으로만 계산한다. 그래야 이전
수치와 비교된다 (키워드룰 커버리지 80.6% 는 변동 없음).

## 3. 우리에만 있음 — 제안 필요 (9 + 1)

| 파서 출력 | 근거 |
|---|---|
| `approval_no` | `natural_key` 유니크 보장에 필수. 실데이터에서 별개 거래 2조합/5행이 같은 키를 받아 적재 거부되는 것을 확인했다. 승인번호 추가 후 충돌 0건. 부수 효과로 취소 페어링이 감사 가능해진다 |
| `biz_no` | 3트랙 1순위 키. 커버리지 74.5%(국내 카드 파일 기준). 20바이트 절단으로 갈라진 문자열을 같은 사업장으로 묶는다 |
| `needs_review` | 취소 불확정 등 자동 판정 불가 상태. 이 필드가 없으면 되묻기 대기 건이 확정된 것처럼 보인다 |
| `review_reason` | 같음. 사용자에게 무엇을 물어야 하는지가 여기 들어간다 |
| `branch` | 학습 룰카드가 지점 단위로 승격할 근거. **`merchant_dict` 에는 저장 금지** — 지점명은 생활권 정보다(같은 편의점 28회 = 거주지 추정). `transaction` / `user_rules` 에만 저장한다 |
| `branch_raw` | 20바이트 절단으로 지점명 추출이 실패했을 때 원문 잔여 부분을 보존한다. 억지 파싱을 하지 않는다는 뜻이기도 하다 |
| `memo` | KB 사용자 메모. 한 상호(구글플레이)가 Onedrive / Gemini / GPT 로 갈리는 **유일한 단서**다. 되묻기 화면에 함께 띄우면 질문을 좁힐 수 있다 |
| `is_aggregated` | 카드사 합산 행(`지하철_모바일 50 건`). 개별 취소 대상이 아니라서 취소 페어링 후보에서 제외한다 |
| `source_card` | 어느 어댑터가 만든 행인지(`ibk`/`kb`/`teammate`). 카드사별 특이사항(IBK 는 취소를 양수로 표기 등)을 추적할 때 필요하다 |
| `norm_key` *(제안. 파서 출력에는 없음)* | `natural_key`(거래 단위)와 **다른 개념**이다 — 가맹점 단위 묶기용. 사업자번호 트랙을 쓰면 키가 숫자라 `merchant_norm`(상호 문자열)으로 대체할 수 없다. 값은 적재 시점에 백엔드 엔진이 계산해야 한다(파서가 박으면 엔진 이중화) |

## 4. natural_key 결함 검증 (백엔드 협의)

스키마 정의는 `hash(approved_at + merchant_raw + amount)` 이고 UNIQUE 다.
실데이터 137건(승인일이 있는 행)에 그대로 적용해 측정했다.

### 변경 전 — 스키마 정의대로

```
실제 중복        0건
별개 거래 충돌   2조합 5행

  ○○ 1,000원  2026-08-30  3건  승인번호 78968731 / 78974100 / 78979670
  ○○ 1,000원  2026-07-18  2건  승인번호 74664632 / 74680367
```

같은 날 같은 가맹점에서 같은 금액을 여러 번 결제한 **실제 거래**다
(정액 반복 결제). 승인번호가 전부 다르다.

**UNIQUE 를 걸면 5건 중 3건이 적재 거부된다.** 실제 지출이 조용히 사라지고,
사용자는 경비를 덜 계상해 세금을 더 낸다. 표본 137건에서 이미 이 정도이므로
1년치를 올리면 수십 건이 된다.

### 변경 후 — 승인번호를 재료에 추가

```
natural_key = hash(approved_at + merchant_raw + amount + approval_no)

별개 거래 충돌    0건
파일 간 실제 중복  5건 (여전히 검출)
```

같은 파일을 두 번 올리는 시뮬레이션에서 5건이 같은 키로 잡혔다. 즉
**중복 차단 기능은 그대로고 오탐만 없어졌다.**

### 승인번호 단독을 키로 쓰지 않는 이유

8자리라 재사용될 수 있고 카드사마다 별개 체계다. 유니크가 보장되지 않는다.
그래서 단독 키가 아니라 기존 재료에 더하는 형태로 구현했다.

### 키 재료의 상호명은 마스킹 전 원본을 쓴다

목적이 "같은 원본 파일을 두 번 올렸을 때 중복 차단"이므로, 원본을 다시
파싱하면 같은 키가 나와야 한다. 마스킹 라벨(`의료_마스킹_01`)은 파싱 순서에
따라 흔들리므로 그것으로 해시하면 재파싱 시 키가 바뀐다.

검증: 행 순서를 뒤집어 재파싱했을 때 키 집합은 동일하고 마스킹 라벨만 바뀌었다.

## 5. 표시용 라벨 안정성 (백엔드 확인 필요)

의료 마스킹 라벨이 재파싱마다 달라진다.

```
정순  키 74af71… -> 의료_마스킹_01
역순  키 74af71… -> 의료_마스킹_03      (같은 거래, 같은 키, 다른 라벨)
```

`natural_key` 는 고정이므로 적재·중복 차단은 문제없다. 다만 화면에
`의료_마스킹_01` 을 그대로 보여주면 재업로드 후 번호가 바뀐다.

**제안:** 표시용 라벨은 DB 가 `natural_key` 기준으로 부여한다. 파서는
마스킹 여부만 표시하고 번호는 DB 가 매기는 방식이다.

## 6. 파서가 읽되 내보내지 않는 것

| 원본 컬럼 | 처리 |
|---|---|
| 카드번호 | 읽지 않는다 |
| 이용고객명 | 읽지 않는다 |
| 이용카드명 | 읽지 않는다 |
| 승인일시의 시각 | 날짜만 남기고 버린다 |

## 7. 알려진 한계

- `installment_months` 파싱은 실데이터로 검증되지 않았다. 표본이 전부
  일시불이라 정규식 단위 확인만 했다. 할부 거래가 들어오면 재확인해야 한다.
- 팀원 데이터(`source_card=teammate`, 189건)는 상호명 한 컬럼짜리 목록이라
  승인일·승인번호가 없어 `natural_key` 를 만들지 못한다. **분석용 데이터이고
  제품 경로(카드 파일 업로드)에는 들어가지 않으므로 정상이다.**
- 외화 전용 행(국내이용금액 0, 해외이용금액 있음)은 원화 환산액이 없어
  현재 제외한다. 표본에는 0건이다.
