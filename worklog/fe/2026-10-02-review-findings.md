# 자기 검토에서 나온 결함 정리

PR 올리기 전에 "정말 되는지" 다시 봤다. 별도 컨텍스트(서브에이전트)에 적대적 검증을
맡기고, 직접 재현한 것만 고쳤다. 전에 "검증 완료"라고 적었던 범위가 좁았다.

## 한 일

### 닿을 수 없던 화면
- `/transactions`, `/uploads` 는 라우트 정의만 있고 **앱 어디에도 링크가 없었다.**
  주소를 직접 쳐야만 들어갈 수 있었다.
- `AppShell` 에 흐름 밖 자료 화면용 `REFS` 내비게이션을 넣었다(거래 · 업로드 이력).
- 원인은 검증 방식이었다. 하네스가 `history.pushState` 로 이동해서 "링크가 있는가"를
  한 번도 보지 않았다. 링크를 눌러 들어가는 `nav` 스위트를 새로 만들었다.

### 화면끼리 숫자가 달랐다
목업 집계가 292건 규모의 가상 데이터였고 거래 시드는 29건이었다. 의도한 설계였지만
(`목업 데이터는 292건 중 24건 샘플` 주석) 화면에 그대로 드러났다.
`/uploads` 292건 · `/transactions` 29건 · `/preview` 분모 292 · `/preview` 확인 필요 5건 ·
`/uploads` 확인 6건.

- `UPLOAD_BATCH` 의 `transactionCount` · `classificationPendingCount` 를 실제 배열에서 계산.
- `judgments.summary` 를 고정값(168/53/71) 대신 `latestAll()` 에서 계산. `JUDGMENT_SUMMARY`
  기준값은 제거했다.
- 미분류 거래에 달려 있던 판정 1건을 뺐다. 미분류는 엔진에 넘어가지 않는다(api.md 3.3).
- `runs.create` 의 판정 대상에 `classificationStatus=CLASSIFIED` 조건을 넣고, 비어 있을 때
  시드 숫자로 가짜 Run 을 만들던 `|| JUDGMENT_RUN.totalCount` 를 없앴다.
- 앱 문구에 박혀 있던 292 를 걷어냈다(`Summary` 의 세무대리인 문장, `Questions` 안내문,
  `sampleFiles.rowCount`). 결과: 거래 31 / 확인 필요 6 / 판정 23 이 전 화면에서 일치.

### 조회 실패를 "데이터 없음"으로 보여줬다
- `Transactions` · `Uploads` 가 `useApi` 의 `error` 를 읽지 않아, 5xx 가 "아직 올린 파일이
  없습니다" + 업로드 유도 버튼으로 보였다. 실패 상태와 `다시 시도` 를 넣었다.
- `ClassificationPreview` 는 로딩 중과 조회 실패에 "모든 거래를 분류했습니다"(tone=ok)를
  띄웠다. 다 읽은 뒤 0건일 때만 그렇게 말하도록 했다.

### 제목과 본문이 다른 말을 했다
- `Run` 은 실행이 404 일 때 본문은 "찾을 수 없습니다", 제목은 "판정하고 있습니다"였다.
- `runId` 도 batch·문진도 없으면 영원히 "판정하고 있습니다 / 0 / 0건 / 예상 남은 시간
  약 40초"였다. 준비되지 않은 상태를 따로 두고, 가짜 남은 시간 문구를 없앴다.
- `FAILED` 인데 실패 목록이 0건이면(명세 2.7) 아무 안내도 없는 막힌 화면이었다.

### 눌러도 아무 일 없던 것들
- `Confirm` 의 판정 시작과 `Run` 의 다시 판정하기에 catch 가 없었다. 실패하면 조용히
  돌아오거나 "다시 실행 중…" 에 영구히 갇혔다.
- `ClassificationPreview` 의 업종 저장도 실패 시 "처리 중" 이 안 풀렸다. setTimeout 정리도 없었다.
- DESIGN.md 109행에 "눌리는데 아무 일 없는 버튼은 만들지 않는다"고 적어 둔 것을 어기고 있었다.

### 집계를 현재 페이지로 하고 있었다
- `ClassificationPreview` 헤더가 그룹 배열을 더했다. 계약 기본 `size` 는 20인데
  (api.md 3.1) **목업이 기본 100 이라 버그가 가려져 있었다.** 목을 20으로 맞추고,
  건수는 `page.totalElements` 를 쓰도록 했다. 금액은 전부 받지 못하면 말하지 않는다.
- #74 가 머지되면 `unresolved{count,amount}` 로 바꾼다.

### 계약과 달랐던 곳
- `QuestionResponseResult` 가 제거된 모양(`{answeredCount, runId}`)이었다. 명세는
  `{answeredCount, factId, rejudgedTransactionCount}` 이고 "새 JudgmentRun 은 만들지
  않는다"(api.md 3.10). 목도 Run 을 만들고 있었다.
- `BulkAnswerResult` 에 `rejudgedTransactionCount` · `unresolved` 가 없었다.
- 404 코드가 `UPLOAD_BATCH_NOT_FOUND` 였다(명세는 `BATCH_NOT_FOUND`). Run 상태 라벨 `진행` → `실행 중`.
- `questions.respond` 가 정적 배열에서 그룹을 찾아, 배치를 지운 뒤에는 404 대신 TypeError 였다.

### 되돌릴 수 없는 동작 · 접근성
- 삭제 실패 문구가 모달 백드롭 뒤에 그려져 눈에 보이지 않았다. 대화상자 안으로 옮겼다.
- `Modal` 에 `aria-modal` 만 있고 포커스 트랩이 없어 Tab 이 뒤 화면으로 빠졌다. 뒤 행의
  「삭제」로 초점이 가서 Enter 로 다른 배치를 지울 수도 있었다. 트랩 · 초점 복귀 ·
  `aria-describedby` 를 넣었다.
- 현재 배치를 지울 때 `runId` 도 세션에서 치운다.
- `FilterBar` 가 `role=tablist` 였지만 tabpanel 도 화살표 이동도 없었다. `role=group` +
  `aria-pressed` 로 바꿨다.
- 행마다 같던 「삭제」 버튼에 `aria-label` 을 붙였다.

### 검증 공백

## 왜 이렇게 했나

- **목을 계약과 다르게 두면 그 차이만큼 화면을 잘못 만든다.** 이번에 두 번 겪었다. 삭제
  연쇄를 안 하던 것(지난번), 기본 page size 가 100 이던 것(이번). 둘 다 목이 더 관대해서
  화면의 버그가 가려졌다. 그래서 숫자·기본값·에러코드는 계약 쪽으로 맞췄다.
- **집계는 목이 흉내 내는 대상이 아니라 계산 대상이다.** 292 고정값에 이동분을 더하는
  방식은 답변·수정이 늘어날수록 틀려진다. 실제 판정에서 계산하면 틀릴 수 없다.
- **"없다"와 "못 읽었다"는 다른 말이다.** 세금 도구에서 서버 장애가 "데이터 없음"으로
  보이면 사용자는 자기 자료가 사라졌다고 읽는다.
- 타입체크를 `build` 에 물린 이유는, 안 돌리면 다시 쌓이기 때문이다. 카테고리 드리프트
  검사와 같은 자리에 뒀다.

## 남은 것 · 아는 문제

- `/upload` 는 브라우저 파서가 없어 아직 표본 파일 선택 방식이다(파서는 `tools/parsers/`
  에 Python 만 있다). `/account` 는 스텁.
- 목의 `uploads.create` 는 거래를 넣지 않는다. 새 파일을 올려도 거래 목록에는 안 나온다.
  `fileHash` 중복 409 · `Idempotency-Key` 도 흉내 내지 않는다. 멘토님이 #71 에서 "목에서
  상태 변화까지 하는 건 차라리 서비스 레이어를 구현하는 게 낫다"고 하셨으므로 여기까지
  두고, 실제 서버 연동 일정을 잡는 쪽으로 간다.
- `judgments.list` 가 `latestOnly` 기본값(true)과 반대로 동작하고 `runId` · `year` 필터를
  무시한다. `transactions.include/exclude` 가 집계에 반영되지 않는다.
- `Upload` · `Interview` · `Results` · `Questions` · `Summary` 는 아직 생 px 가 남아 있다.
- `Run` 의 폴링은 1초 간격이다. 실서버에서 처리 시간이 길어질 때 버티는지는 확인하지 못했다.
- 실패 목록과 실패 거래 조회가 100건 상한이다. 그 위는 이름 없이 id 로 보인다.

## 덧붙임 — PR 올리기 직전에 두 건 더

### 제외한 거래가 집계에 남아 있었다
- 거래를 판정 대상에서 빼도 `/results` · `/summary` 숫자가 그대로였다. 명세는
  "사용자가 현재 EXCLUDED 한 Transaction 은 제외한다"(api.md 3.7, 1435·1506행)다.
- `judgments.summary` 와 `judgments.list` 에서 `effectiveStatus !== JUDGEABLE` 을 뺀다.
  거래별 이력 조회(`transactionId` 지정)는 그대로 전체를 준다.
- 확인: 「불가」거래 1건 제외 → 전체 23→22, 불가 7→6. 다시 포함 → 23/9/7/7 복구.

### 내가 잠재 결함을 살려 놨다
- `Table` 의 `onRowClick` 행은 `tabIndex` · `onKeyDown` 이 없어 마우스로만 눌렸다.
  부품 주석에는 "행 전체가 버튼처럼 동작한다"고 적혀 있었다(거짓).
- 쓰는 화면이 없어 잠재 결함이었는데, 이번에 스타일가이드 예시에 `onRowClick` 을
  넣으면서 실제로 살아났다. `tabIndex` · Enter·Space · 포커스 링 · `aria-current` 를 넣었다.
- 확인: 행에 포커스 → Enter 로 해제, Space 로 선택.

## 덧붙임 2 — 스크린샷을 찍다가 알게 된 것

### 내 검증은 눈으로 본 적이 없다
PR 에 붙일 스크린샷을 찍었더니 CSS 가 하나도 안 걸린 생 HTML 이었다. 중간에
`npm ci` 로 `node_modules` 를 갈아엎으면서 돌고 있던 dev 서버가 깨진 것이다.
그런데 그 동안 돌린 스위트는 **전부 통과했다** — 텍스트와 DOM 만 보기 때문이다.

그래서 CSS 가 있어야 의미가 있는 검사 두 개는 그때까지 아무것도 확인하지 못했다.
- `hideBelow` 열 표시 확인: `isVisible()` 은 스타일이 없으면 전부 true 다
- 가로 스크롤 검사: 스타일이 없으면 넘칠 일이 없다

서버를 다시 띄우고 CSS 가 올라오는지(규칙 450개, 토큰 색 적용) 먼저 확인한 뒤
전부 다시 돌렸다.

### 좁은 화면에서 글자가 한 자씩 세로로 떨어졌다
`hideBelow` 를 "핵심 정보에는 쓰지 않는다"는 규칙대로 분류 열에서 떼어냈더니,
390px 에서 그 열이 눌려 「분류 확인 필요」가 글자 하나씩 세로로 쌓였다. 규칙은
지켰는데 읽을 수 없게 됐다.

- `Badge` 에 `whitespace-nowrap`. 배지는 어떤 폭에서도 줄바꿈하지 않는다
- 분류 열은 다시 `hideBelow` 로 숨기되, **그 정보를 가맹점 칸으로 옮긴다**
  (`md:hidden` 으로 좁은 화면에서만 보이는 배지). 숨기는 것과 없애는 것은 다르다
- 표에 최소 폭을 줬다가 되돌렸다. 폭을 잡으니 금액 열이 스크롤 뒤로 밀렸다

확인 방법도 바꿨다. `isVisible()` 대신 **실제 크기를 잰다** — 배지 높이가 40px 를
넘으면 눌린 것이다. 390 · 768 · 1280 세 폭에서 본다(`squish` 스위트).

### 남은 한계
390px 에서 표 폭이 492px 라 금액·판정 대상은 표 안에서 가로로 조금 밀어야 한다.
페이지 자체는 넘치지 않고 날짜·가맹점·분류는 바로 보인다. 5개 항목짜리 금융
표를 390px 에 다 넣으려면 표가 아니라 카드 목록이어야 하는데, 이번 PR 범위를
넘어서 두고 적어 둔다.
