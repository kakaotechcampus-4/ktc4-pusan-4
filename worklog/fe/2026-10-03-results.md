## 왜 이렇게 했나

- **`runId` 를 버린 이유**: 명세상 `runId` 는 그 Run 이 만든 판정만 준다(3.7). 답변·수정은 새 Run 없이 revision 만 만들어서, `runId` 로 읽으면 답해도 숫자가 그대로다. 목업이 `runId` 에도 현재 판정을 돌려줘 드러나지 않았다.
- **Run 이 revision 을 남기게 한 이유**: `runId` 를 계약대로 좁히자 목업 Run 이 판정을 남기지 않아서, teammate 의 `/run` 이 판정을 마치고도 「가능 0 · 확인 필요 0 · 불가 0」이었다. 계약대로 좁히면 목업의 다른 쪽도 함께 따라와야 한다.
- **패널이 따로 읽는 이유**: 목록은 `computedAt DESC` 라 수정한 행이 맨 위로 올라간다. 다른 페이지·필터에 있던 행을 수정하면 목록에서 사라지는데, 패널까지 바뀌면 방금 한 일을 확인할 수 없다. 또 이전 거래의 응답을 새 거래 이름 아래 그리면 수정이 엉뚱한 판정에 걸린다.
- **수정 사유**: `reason` 은 `JudgmentOverride` 에 남는 기록이다. 고정값 「사용자 직접 수정」으로는 왜 바꿨는지 알 수 없다. 확인 필요로의 수정은 #62 논의대로 두지 않았다.
- **③ 을 질문으로 판단한 이유**: origin 으로 보면 다시 판정한 뒤 RUN 으로 바뀌어 안내가 사라진다. 문구를 「인정된다」고 단정하지 않은 것은, R-300 혼자작업처럼 조문만으로 갈리지 않는 답도 ③에 들어가기 때문이다.
- **소명 대기를 따로 보인 이유**: develop 의 주말·공휴일 카드(R-311~314)는 「기본 불가, 소명하면 가능」이다. 확정 불가처럼 보이면 사용자가 답할 이유를 모른다.
- **「추론」 배지를 뺀 이유**: 규칙이 없어 근거를 비워 둔 판정을 모델이 추정한 것처럼 읽히게 했다. 원칙 2(근거를 지어내느니 비워 둔다)와 어긋난다.

- 결과 목록은 한 페이지에 `transactions.get` 을 최대 20번 부른다. 판정 목록 응답에 거래 요약이 붙으면(#74 와 같은 방식) 한 번으로 준다. BE 와 상의가 필요하다.

- 자산 금액을 사용자가 줄여 넣는 기능은 API 필드가 없어 「까지」 문구만 맞췄다.
- 고시를 「참고 해석기준」으로 둘지(CONTEXT.md §6)와 위임 고시를 확정 근거로 쓰는 ai/pipeline 이 어긋난다. 팀 확인이 필요하다.
- 공용 `Table`(A파트)은 행에 버튼 역할·이름이 없고 선택을 옅은 바탕으로만 보여준다. 손대지 않고 가맹점 칸에 점만 붙였다.
- ③ 문구가 docs/rule-card-fields.md 의 「인정됩니다. 안분 비율만 정하면 됩니다」와 다르다. 혼자작업 같은 답에는 그 문구가 틀려서 바꿨는데, 문서 쪽을 고칠지 팀 확인이 필요하다.
- 목록에서 ③(답했지만 남음)은 다른 확인 필요와 같은 배지다. 행마다 질문 상태를 읽어야 해서 패널에서만 나눈다.
- 목업 `now()` 가 UTC 라 수정 시각이 9시간 이르게 보인다. 실서버 응답은 `+09:00` 이다.
- 검증: 관점별 리뷰 + 반박 검증을 세 차례 돌려 살아남은 지적을 고쳤다. 마지막 두 차례는 브라우저 연결이 안 돼 타입체크·빌드, 목업을 node 로 돌린 확인, jsdom 렌더 확인으로 대신했다.

- 목업 질문을 develop 의 `rules/cards` 에서 옮겼다(R-300 카페, R-303 편의점, R-208 여비교통, R-205 통신, R-103 수도광열, R-107 해외SaaS 고액).
  - 답하면 그 카드의 선택지대로 판정·규칙 카드·계정과목·근거·속성을 붙인다. 카드가 계정과목을 주지 않으면 비운다. verdict 가 없는 선택지(혼자작업·공용·자택 겸용·연간 일시불)는 확인 필요로 남는다(③).
  - 토요일 한우마을 결제를 R-311 소명 대기(기본 불가 + 소명 질문)로 바꿨다. 일괄 답변은 소명 대기를 빼고 건너뛴 수에 넣는다.
  - 미분류 거래의 질문은 뺐다(미분류는 엔진에 넘기지 않는다, api.md 0.5).
  - 응답은 질문 id 를 검증하고(404·409), 정정·일괄 답변마다 UserFact version 을 올린다. `unresolved` 는 `transactionId` 필터를 따르고 금액은 거래당 한 번만 더한다.

### 왜

- **일괄 답변을 5개 이하에서만 연 이유**: 처음부터 보이면 첫 화면에서 전부 「개인」으로 닫아버릴 수 있다(F1 문서의 미정 안건). 사용자와 상의해 F1 문서가 제안한 「남은 건이 적을 때만」으로 정했다.
- **목업 질문을 카드에서 옮긴 이유**: 전에는 모든 질문이 factType 「용도」인데 선택지가 제각각이라 일괄 답변이 어떤 값으로도 422 였다. 카드의 선택지대로 계정과목·근거를 붙이지 않으면, 통신 「전용」 답이 소모품비로 잡히고 가능 판정에 「가사 경비는 산입하지 않는다」가 근거로 붙었다.
- **페이지로 넘기는 이유**: 건너뛴 카드가 앞자리를 차지하면 뒤 질문에 닿을 수 없었다.
- **거래 줄을 질문에서 찾는 이유**: 「확인 필요 거래 100건」과 잇던 탓에, 사용자가 판정을 바꾼 거래나 100건 너머의 질문은 줄이 비었다.
- **소명 대기를 일괄 답변에서 뺀 이유**: develop 의 휴일 카드도 평일 카드와 같은 「용도」를 쓴다. 「전부 업무미팅」 한 번이면 주말 불가 추정이 소명 없이 모두 풀린다(rule-card-fields.md). develop 의 BE 일괄 응답은 아직 고정 목 응답이라 소명 대기를 빼지 않는다.

### 남은 것

- 질문 응답에 답한 값이 없다(`answeredFactId` 만 있다). 「「개인」으로 답함」은 이번 화면에서 고른 것만 보이고, 새로고침하면 「답함」으로만 보인다.
- 카드의 거래 줄은 질문 목록을 100건씩 넘기며 찾고 거래·현재 판정을 하나씩 받는다. 그룹 응답에 거래 요약이 붙으면(#74 와 같은 방식) 한 번으로 준다.
- 답을 고르는 즉시 저장하는 방식이라, 화면 낭독기에는 고른 선택지가 저장이 끝난 뒤에야 선택됨으로 읽힌다.
- 목업 조문 목록에 §35① 원문이 없어 카페 「업무미팅」 가능 판정에 근거가 비어 보인다. 실서버는 카드의 선택지 근거를 붙인다.
- 일괄 답변 노출 기준(5개)과 한 번에 보여줄 수(15개)는 잠정값이다. 거래 시드의 카테고리(「소프트웨어」·「교통」·「접대·식음료」 등)는 2.12 어휘가 아니라 카드 매칭 조건과 글자 그대로 맞지는 않는다.
- 수정한 거래 안내와 소명 대기 판단은 카드에 보이는 거래(그룹당 3건)만 본다. 가맹점 묶음에 거래가 더 많으면 놓칠 수 있다.
- 답한 질문 목록은 100개까지만 받는다. 그 너머의 답은 이 화면에서 바꿀 수 없다.
- 영문으로 끝나는 선택지에는 「로」를 붙인다(발음 판정은 하지 않는다).
