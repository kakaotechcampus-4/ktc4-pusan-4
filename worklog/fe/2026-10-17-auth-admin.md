# 로그인을 api 층 뒤로 옮기고, 관리자 규칙 후보 화면을 목으로 만들었다

- 브랜치: feature/auth-admin (feature/fe-api-sync 위)
- 커밋: fc538e1..177c0f5 (2개)
- 주요파일: frontend/src/api/http.ts, frontend/src/contexts/SessionContext.tsx, frontend/src/pages/Login.tsx, frontend/src/pages/Admin.tsx

## 한 일

- **로그인** — #139 에 적은 대로 가정하고 만들었다. 액세스 토큰은 메모리에 두고 `Authorization` 헤더로, 리프레시 토큰은 서버의 httpOnly 쿠키다
  - 계약에 `auth.login·restore·logout·onLost` 를 두고, 토큰은 `http.ts` 안에만 둔다. 화면은 토큰을 보지 않는다
  - 401 이면 재발급을 한 번 해 보고 같은 요청을 다시 보낸다. 동시에 받은 401 은 재발급 하나를 나눠 쓴다. 재발급도 실패하면 `onLost` 를 한 번만 부르고 세션을 비운다
  - 로그인·재발급 요청에는 토큰을 싣지 않는다. `/auth/*` 의 401 은 재발급하지 않는다
  - 새로고침하면 `restore`(재발급)로 로그인을 이어 간다. 그동안(`restoring`) 보호된 화면은 비워 두고 로그인 화면으로 보내지 않는다. 랜딩 헤더도 버튼을 비워 둔다
  - 실서버에서 로그인하면 가장 최근 업로드로 시작한다. 목업은 시드 배치 그대로다
  - 로그아웃은 토큰을 실어 보내고 바로 지운다. 서버 응답은 기다리지 않는다. 탈퇴도 같은 길로 비운다
  - 로그인 화면은 실제로 로그인을 부르고, 401·연결 실패·그 밖을 정해진 문구로 알린다. 카카오·샘플 계정 버튼은 목업에서만 보인다
  - 경로는 `/auth/login`·`/auth/refresh`·`/auth/logout`, 응답은 `{accessToken}` 으로 가정했다
- **관리자(M1)** — `/admin`. 상태별(대기·보류·승인·기각) 규칙 후보, 근거(조문·위계·인용), 초안 YAML, 검토한 사람·시각을 보이고 승인·기각한다
  - 관리자는 `users/me` 의 `role: 'ADMIN'` 으로 가린다(가정). 관리자에게만 헤더에 「관리자」 링크가 보이고, 아니면 `/admin` 에서 `/upload` 로 보낸다. 403 이면 「관리자만 볼 수 있습니다」
  - 승인·기각은 확인 대화상자를 거친다. 초안이 없는 보류 후보는 기각만 된다. 이미 처리한 후보는 409 로 막고 목록을 다시 읽는다
  - 목업은 `admin@…` 으로 로그인하면 관리자다. 후보 4건(대기 2·보류 1·승인 1)
- **테스트** — http 인증 6건(헤더, 재발급·재시도·나눠 쓰기, 한 번만 알림, 로그인 401, 이어 가기 실패, 로그아웃), 목업 로그인·관리자 2건

## 왜 이렇게 했나

- 토큰을 api 층에만 둔 것: #139 의 답(엔드포인트·만료·로그아웃 범위)에 따라 바뀌는 곳을 `http.ts` 하나로 묶는다. 화면과 세션은 `login`·`restore`·`logout` 만 안다
- `onLost` 에서 로그아웃을 부르지 않는 것: 이미 풀린 세션이라 로그아웃도 401 이고, 그 401 이 다시 재발급·알림을 부른다
- 토큰이 있을 때만 `onLost` 를 알리는 것: 동시에 실패한 요청마다 알리면 세션 비우기가 여러 번 돈다
- 로그인·재발급에 만료된 토큰을 싣지 않는 것: 서버가 헤더의 토큰부터 검사하면(Spring 의 Bearer 필터처럼) 허용된 경로라도 거기서 401 이 난다
- 가장 최근 업로드로 시작하는 것: 보던 배치는 메모리에만 있다. 새로고침으로 로그인을 이어 가면 모든 화면이 「올린 카드내역이 없습니다」가 된다. 3.3 목록이 `createdAt DESC` 라 첫 줄이 최근 것이다
- 카카오·샘플 계정을 목업에만 둔 것: 인증 방식(카카오 OAuth, 자체 JWT 등)이 정해지지 않았다(`backend_api_plan.md`). 실서버에서 누를 수 없는 버튼을 두지 않는다. 회원가입은 어디에도 계약이 없어 만들지 않았다
- 관리자 링크를 헤더에 둔 것: 새 화면은 STEPS·REFS 에 링크가 있어야 한다(DESIGN.md). 관리자에게만 보인다
- 보류 사유를 보이지 않는 것: `rule_candidate` 에 사유 칼럼이 없다(#94). 지어서 보여 주지 않는다

## 확인

- `npm run build`·`npm test`(127개 통과, `parity.test.ts` 는 건너뜀)·`npm run lint`(오류 0, 기존 경고 10건), `VITE_API=http` 빌드 통과. 커밋마다 따로 타입 검사·api 테스트를 돌렸다
- 목업으로 띄워 확인했다(콘솔 오류 없음)
  - 로그인 전에 /results 로 들어가면 /login 으로 가고, `admin@example.com` 으로 로그인하면 /results 로 돌아온다. 저장하는 동안 버튼이 「로그인 중…」
  - 관리자 헤더에 「거래·업로드 이력·관리자」. 승인 → 대화상자(초점이 안으로) → 「…후보를 승인했습니다」, 대기 목록이 2 → 1. 보류 후보는 승인 버튼이 꺼져 있고, 승인 탭에 「admin@example.com · … 처리」
  - 일반 계정은 관리자 링크가 없고 /admin 에서 /upload 로 간다. 로그아웃·탈퇴 뒤에는 / 로 가고, 보호된 화면은 /login 으로 보낸다
  - 관리자 링크가 붙은 헤더를 768·800·1023·1024·1100·1279·1280px(/results, 단계 표시 있음)에서 재 보니 줄바꿈 0, 넘침 0. /admin 은 375px 에서 가로로 넘치지 않는다(같은 오리진 iframe 으로 폭을 맞춰 쟀다)
- `VITE_API=http` 로 띄우고 프록시를 닫힌 포트로 돌려(외부로 나가지 않게) 확인했다
  - 버튼은 「로그인」 하나뿐이다. 부팅 때 `POST /auth/refresh` 한 번, 로그인 때 `POST /auth/login` 한 번
  - 프록시 오류(500)에는 「로그인하지 못했습니다」가 뜬다

## 남은 것 · 아는 문제

- 경로·응답 모양·만료·로그아웃 범위는 #139 답을 보고 `http.ts` 에서 맞춘다. 리프레시 쿠키에 `Domain=` 이 붙으면 vite 프록시 뒤(개발)에서 브라우저가 쿠키를 버린다. 그때 `cookieDomainRewrite` 를 쓴다
- 관리자 판별 방식과 승인 뒤 처리 범위는 10/26 에 정한다. 경로·모양은 가정이다
- 목업은 새로고침하면 로그인이 풀린다(전과 같다)
- 이 브랜치와 `feature/assistant-panel` 은 둘 다 `feature/fe-api-sync` 위에 있다. 같은 worklog 에 이어 쓰면 머지할 때 부딪혀서 따로 문서를 두었다
